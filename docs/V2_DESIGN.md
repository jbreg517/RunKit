# RunKit v2 — Design Sketch

> Companion to `REQUIREMENTS.md` (scope) and `DIFFERENTIATION.md` (why).
> Status: **sketch, not committed scope.** v2 is the differentiation release —
> it turns RunKit from "a good private tracker" into "the only run app that
> knows you lifted yesterday."

The four tentpoles build on each other in this order. Each is shippable alone.

```
  Calendar  ──►  Plan generator  ──►  Recovery-aware scheduling
  (surface)      (fills it)           (adapts it)   ▲
                                                    │
                                        Readiness ──┘  (also standalone)
  Watch app ── parallel track, no dependency
```

---

## 1. Planning calendar (the surface)

LiftKit-style month/week calendar. Without it the other three have nowhere to live.

### Model — new `PlannedWorkout`
```swift
@Model final class PlannedWorkout {
    var id: UUID = UUID()
    var scheduledFor: Date = Date()          // day granularity
    var typeRaw: String = ActivityType.run.rawValue
    var workoutTypeRaw: String = WorkoutType.free.rawValue   // reuse v0.15 enum
    // Structured params mirror ActivitySession so a plan can pre-fill a session.
    var targetDistanceMeters: Double = 0
    var targetSeconds: Double = 0
    var intervalWork: Double = 0
    var intervalRest: Double = 0
    var intervalReps: Int = 0
    var paceTargetSecPerMeter: Double = 0
    var title: String = ""                   // "Easy 5K", "6×400m"
    var notes: String?
    var planID: UUID?                        // set when generated by a plan
    var weekIndex: Int = 0                   // position within the plan
    var completedSessionID: UUID?            // links to the ActivitySession
    var adjustedReason: String?              // set by recovery-aware scheduling
}
```
CloudKit-compatible per house rules: non-optional attrs defaulted, relationships optional.

### Behaviour
- **Calendar tab** (or a segment inside History) — month grid, dots per day:
  gold = planned, filled = completed, hollow = missed.
- Tap a day → planned workouts + any actual sessions recorded that day.
- **"Start this"** on a planned workout deep-links into `ActivitySessionView` with
  `workoutType` and params pre-filled — the whole point of matching field names.
- **Completion matching**: on `finalize()`, look for a `PlannedWorkout` on the same
  day with a matching type; link it via `completedSessionID`. Manual override in
  the day sheet ("mark as done / skip").
- Fully usable **without** a generated plan — you can hand-place workouts.

## 2. Training-plan generator (fills the calendar)

Entirely on-device, deterministic — no model, no network. This is what Strava
paywalls and Nike gates behind login.

### Input
Goal distance (5K / 10K / half) × current level (beginner / returning / regular)
× race date (or "just get fitter" → rolling 8 weeks) × days per week (3–5).

### Model — new `TrainingPlan`
```swift
@Model final class TrainingPlan {
    var id: UUID = UUID()
    var goalRaw: String = ""                 // "5k" | "10k" | "half" | "base"
    var levelRaw: String = ""
    var startDate: Date = Date()
    var raceDate: Date?
    var daysPerWeek: Int = 3
    var isActive: Bool = true
}
```

### Generation
Ship plan **templates as data** (a `[PlanWeek]` blueprint per goal×level, JSON in
the bundle), not as generated prose. Each week is a set of slots:

```
slot = (dayOffset, kind, volume)
kind ∈ { easy, long, tempo, intervals, rest, crossTrain }
```

The generator:
1. Picks the template for goal×level, truncates/stretches to fit the weeks available.
2. Scales volume from the user's recent 4-week average distance (from
   `ActivitySession` history) rather than a fixed table — so it fits real fitness.
3. Applies progressive overload with a **down week every 4th** (~70% volume).
4. Maps each slot onto a concrete `PlannedWorkout` with real params:
   - `easy` → distance target at conversational pace
   - `tempo` → `.pace` workout with a computed `paceTargetSecPerMeter`
   - `intervals` → `.intervals` with work/rest/reps (e.g. 6×400m)
   - `long` → distance target, biggest of the week
5. Writes them into the calendar; taper in the final 1–2 weeks before `raceDate`.

**Pace derivation:** estimate threshold pace from the user's best recent effort
(Riegel formula for equivalent race times), then set easy = threshold + ~90 s/km,
tempo ≈ threshold, intervals ≈ threshold − 15 s/km. All on-device arithmetic.

### Free structured-workout library (ships earlier, in v1.1)
The same `PlannedWorkout` params power a static library — C25K, tempo, fartlek,
hill repeats, Yasso 800s — selectable without any plan. Build this first; the
generator is "the library, sequenced."

## 3. Recovery-aware scheduling (the moat)

**This is the feature no competitor can copy**, because it needs cross-domain data
that only the suite writes into one HealthKit bus.

### Signals read (all HealthKit, all opt-in, all on-device)
| Signal | Type | Use |
|---|---|---|
| Strength workouts | `HKWorkout` (functionalStrengthTraining / traditionalStrengthTraining) — **written by LiftKit** | Detect heavy lower-body load in the last 24–48 h |
| HRV | `heartRateVariabilitySDNN` | Deviation from 7-day baseline |
| Resting HR | `restingHeartRate` | Deviation from 7-day baseline |
| Sleep | `sleepAnalysis` | Hours vs. personal average |
| Recent run load | own `ActivitySession` history | Acute:chronic workload ratio |

### Adjustment rules (transparent, rule-based — not a black box)
Compute a 0–100 `readiness` (see §4), then the morning of a planned workout:

- `readiness < 40` **or** a heavy strength session within 24 h → downgrade one
  step: `intervals → tempo → easy → rest`. Set `adjustedReason` so the UI can
  say **why** ("You squatted heavy yesterday — this is an easy shakeout").
- `readiness > 80` and the plan calls for `easy` on a non-recovery week → offer
  (never force) a small volume bump.
- Never adjust more than one step, never two days running — avoids the
  death-spiral where one bad night derails a plan.
- **Always overridable.** The user can restore the original with one tap; RunKit
  suggests, it does not police. (Principle 4: honest estimates, no dark patterns.)

### Boundaries
- Requires HealthKit permission; degrades gracefully to a plain plan without it.
- If LiftKit isn't installed there's simply no strength signal — the feature still
  works on HRV/sleep/run-load alone.
- Explicitly **not** medical advice; label as an estimate, same as calories.

## 4. Readiness score (standalone, also feeds §3)

A single 0–100 number on the Today tab, free — what Athlytic/Gentler Streak charge for.

```
readiness = 100
  − w1 · max(0, (restingHR − baselineRHR) / baselineRHR)        // ↑RHR = fatigue
  − w2 · max(0, (baselineHRV − HRV) / baselineHRV)              // ↓HRV = fatigue
  − w3 · sleepDebt(last night vs. personal average)
  − w4 · acuteChronicExcess(7-day load ÷ 28-day load, over 1.3)
```
Baselines = rolling 7-day medians (median, not mean — robust to one bad night).
Show the **contributing factors**, not just the number; a bare score users can't
interrogate is exactly the black-box pattern we avoid. Needs ≥7 days of data
before displaying anything — say "building your baseline" until then.

## 5. Apple Watch app (parallel track)

Independent of 1–4; the standard cardio expectation.

- **New WatchKit target** in `project.yml` (XcodeGen handles it — same pattern as
  the `RunKitWidgets` extension added in v0.16). Third bundle ID
  `com.ferrixguild.runkit.watchkitapp` → needs its own App ID + profile in the
  signed workflow, same as the widget.
- **Phone-free sessions:** on-wrist GPS + heart rate, `HKWorkoutSession` +
  `HKLiveWorkoutBuilder` (the Watch-only API that keeps the app running).
- **Heart rate is the big unlock** — it makes zones, better calorie estimates, and
  a much better readiness score possible; the phone can't measure it live.
- Sync sessions to the phone via `WCSession` **or** simply let both write to
  HealthKit and dedupe on read — the latter is far less code and fits the
  "HealthKit is the only bus" principle. Prefer it.
- Complications for one-tap start.
- Voice cues route to AirPods from the Watch — the existing `VoiceCue`/clip pack
  is portable, but the clip bundle would need to ship in the Watch target too.

## 6. Premium tier (mirrors LiftKit)

Anti-subscription positioning (see `DIFFERENTIATION.md` §3). Suggested split:

| Free forever | Plus (one-time unlock) |
|---|---|
| All tracking, GPS routes, HealthKit, structured workout types, voice coach (deadpan), history, export | Plan generator, recovery-aware scheduling, extra coach personalities, calendar beyond the current month |

Non-negotiable: **nothing already free becomes paid**, and export stays free —
data portability is a principle, not a feature. StoreKit-only, anonymous, no
sign-in (same decision as LiftKit).

## 7. Build order & risk

| # | Item | Risk | Notes |
|---|---|---|---|
| 1 | Workout library (v1.1) | Low | Data-only; de-risks the plan generator |
| 2 | Calendar + `PlannedWorkout` | Med | New model + tab; migration is additive |
| 3 | Plan generator | Med | Pure logic, unit-testable, no new frameworks |
| 4 | Readiness score | Med | New HealthKit read types → permission changes |
| 5 | Recovery-aware scheduling | High | Depends on 2+3+4; needs LiftKit data to test |
| 6 | Watch app | High | New target, new signing identity, on-device-only APIs |

**Open questions**
- Does the calendar warrant its own tab (5 tabs) or a segment in History? Leaning
  own tab — it's a tentpole, and LiftKit users will expect the parallel.
- SwiftData migration: adding new `@Model` types is additive and safe, but confirm
  before shipping to real TestFlight users with data.
- Watch voice cues: ship the clip pack twice (bundle size) or fall back to system
  TTS on the Watch? Leaning system TTS on Watch.
